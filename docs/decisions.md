# Decisions

Owner decisions for this repository, newest last.

## 2026-11-11

- **Do not show who reads next.** In the two-player sample the lines alternate, so the screen shows only the lines read so far and the current one. When the newest line is yours, it is your turn.
- **Font: Shippori Mincho.** Bundled as a woff2 subset of the story text's characters (`samples/hundred-arms/src/fonts/`) and rebuilt when the script's characters change (steps in `CLAUDE.md`).
- **Chat-style screen with icons.** Lines appear as chat bubbles with the speaker's icon; your role's lines on the right, the other role's on the left. Icons are assumed to exist (`public/assets/icon-<role>.webp`, also used by the manifest's character select); the current files are placeholders: Noto Color Emoji glyphs (🗡️ for 勇, 🐙 for 百) rendered once to webp, so they look the same on every device.
- **Light theme, usual chat-app colours.** Soft grey page (not pure white); the current line is white, or a calm blue when it is yours; read lines sit on quieter bubbles with full text contrast. Tokens live in `samples/hundred-arms/src/theme.css`; screens use those variables, never raw colours. Every text colour meets WCAG AA (4.5:1); no opacity fades on resting states.
- **Post-game screen shows the afterword.** After the last line, the title and end mark hold for a moment, then they fade out and the post-game screen fades in after them (200 ms each, one at a time, instant with reduced motion): the centred greeting `review.heading` and under it an area labelled `review.afterword` holding the author's afterword (`afterword` in `script.json`, the author's words verbatim, CC BY 4.0 with the script). No tap needed.
- **Design covers function only.** Design here means helping players see what to do and keeping cognitive load low; decoration (hues, typeface, icon art) is out of scope. Screens are checked against six things to avoid: excess motion (stutter counts), unclear state or action, no clear focus, the eye drawn elsewhere, reading the obvious, and eye travel. Details in `docs/design.md`.
- **Show what to do on your turn.** Right under the newest line, both players see the advance button: filled for the reader, greyed for the other. It says `hint.readThenTap` until your first line is read, then shows the next mark alone; on the last line it says `button.end` instead. Tapping elsewhere does nothing. Each line shows the speaker's name; in the top band your role's icon has a double circle, and band text is bold.
- **Fonts by role.** Story text in Shippori Mincho, UI text in BIZ UDPGothic (Google Fonts, bundled as subsets like the mincho), as two CSS variables. No text below 16px.
- **The line being read matches the button.** When you read, your current line takes the advance button's blue (light, saturated, dark text). The other role's lines are always white.
- **The band shares the HUD's row only when the HUD is narrow.** Whether the top band gets its own row under the UZU HUD is decided by the HUD's share of the screen width: over a quarter (upright phones) it gets its own row; a quarter or less (landscape, tablets) it sits beside the HUD on the same row.
- **Any number of players, and one player reading several roles.** The engine takes any player count; UZU documents no upper limit (`playerCount` is 1 or more), and its catalogue lists works for up to five. Each seat plays a part (a manifest character) that can hold several roles, as in `samples/mittsu-no-takara`. Details in `CLAUDE.md`, Players and parts.
- **Stage directions have no background.** They read as narration, as plain text across the chat column; the advance button alone shows whose turn it is.
- **Ruby above the word, at half size.** Readings from the script show as ruby above their word, the one exception to the 16px minimum, rather than inline in brackets at full size. Ruby may run past its word instead of spreading the word's letters.
- **A stage direction you read gets side lines.** While you read a stage direction, a line in the advance button's colour stands at each side of it, instead of colouring the whole block.

## 2026-11-13

- **Overflow is checked on the drawn screens.** A CSS lint cannot tell whether something spills over, since that depends on the text and the screen size. `capture.mjs --check` walks the screen-preview screens in both orientations in Playwright and lists boxes past the screen or their parent, text and images under the safe area or the HUD, and cut-off content. Chosen over Galen (a layout spec per screen; unmaintained) and BackstopJS (pixel diffs show change, not overflow).
- **InterstellarBG takes the toolkit as a git submodule.** The new work (`KTakahiro1729/InterstellarBoardGame`) is where the toolkit grows the least it needs; it pins a toolkit commit and moves it on when the toolkit changes.
- **General features go into the toolkit.** Whatever the work needs that another work could use (phases, the handout screen, game selection, playing-card parts) is built here; only the work's own content (script, handout text, its games' rules) stays in the work.
- **A work runs as phases.** A work is a fixed list of phases in order; a read-through is one phase and a work can have several. Details in `CLAUDE.md`, Phases.
- **Unwritten parts are empty phases.** A phase whose content is not decided yet (in InterstellarBG, 「その時……」 and the ending until their scripts exist) is an empty phase: the band names it and a next button that any player can tap moves on. How 「その時……」 mixes reading and a game is open until its script exists.
- **Secrets are hidden on screen only.** Secrets such as a word-wolf topic or a hand of cards are hidden on screen only. Shared state reaches every player, and no secrecy mechanism is built.
- **Handout (HO) phase.** Every player reads the shared text and their own part's text, fills in the settings their part asks for, and taps done; the phase ends when everyone is done. Done needs every setting filled in, except those the data marks `optional`. A player can take done back while the phase lasts, which unlocks their settings and the extension button again. Settings stay in the phase state by part and setting ID, so later phases can use them. Labels come from the work's data; the screen's own labels from `strings.json`.
- **Handouts in tabs.** A handout is read in tabs (shared text, your part, impressions, settings) so a long one does not run as one scroll. The tabs come from the handout's existing sections, so the data needs no extra field. The same tabs open read-only from the footer once the phase is over.
- **Handouts readable by everyone after the game.** The post-game phase can show every part's handout and the answers its player filled in (`HandoutReviewView`), in the same tabs as the handout sheet, since each player writes settings and comparing them is the talking point of the post-game talk. It reuses the handout tabs; the work only names the handout phase to read from.
- **HO reading time.** A timer shows the time left (the work sets it; 5 minutes in InterstellarBG). When it runs out the phase ends, done or not; settings left blank stay empty. Before that, any player still reading can ask for more time, which adds 2 minutes for everyone. After it ran out, the next screen keeps that button until anyone acts there; it brings everyone back to the handout with 2 minutes from then. Going back is a general phase feature (`reopen`): the next phase's state is dropped and set up again. Time is the SDK's game time, so actions stay deterministic.
- **Playing cards keep their court figures.** The deck is Adrian Kennard's CC0 SVG cards with the figure art on J, Q and K (about 310 KB for 54 cards), not a plain version; each face loads the first time it shows.
- **Going back only at the step after the handouts.** The one way back in a work is the step right after the handout phase, which returns to the handouts. In the game-select phase a game cannot be left while it runs; back to the list appears once the game is done.
- **A spectator part sits out games that take one fewer.** A game that does not fit the player count is hidden, unless it fits once the work's spectator part steps out; that part then watches (in InterstellarBG, the half-GM part).
- **The footer is the main action area.** Every screen's main actions (advance, next, the handout's time, extension and done, back to the list) sit centred in a footer along the bottom edge, the same place in every phase. In a work of more than one phase it also holds, quieter, the phase list and, once the handout phase is over, the handouts; each opens as a sheet over the current screen for that player alone, and a phase change closes it. Landscape keeps it to one row.
- **Buttons say what they do.** Every button names its action, and whether to press it shows at a glance. Taking back done is a separate button that names what it undoes, not the done button changing its label. Who is done shows as a check on the band's icons, with no count.
- **The phase list is read-only.** It shows the work's phases in order, numbered, with the current one marked. In densetsu-no-tantei the phase list belongs to the admin seat (the manifest's `admin`), where a tap moves everyone; here no jump, no admin seat and no harness-only jump are built.
- **Function in the toolkit, look in the work.** Whatever helps players see what to do (layout parts, buttons, timers, waiting, voting and watching, the frame of a game) is the toolkit's. A work's look (colours, world, art, effects) is entirely the work's: InterstellarBG sets its own colour tokens. The toolkit's `theme.css` holds neutral defaults for the samples.
- **Parts moved from the work to the toolkit.** Chosen by comparing InterstellarBG with the official sample 伝説の探偵 and keeping what both need and is function, not look: one `Button` (primary, secondary, pressed), `TimeLeft` for timers, vote counting (`tally`, `soleTop`), and `watching` for a seat that sits a game out. Left to a later decision: the deal button each card game has.
- **Games show the turn as the read-through does.** Your turn: your filled button. Another player's turn: their block on white. No outlines or tints.
- **A reading work ships only reading parts.** The playing cards' images reached every build through the reader's main entry (a 145 KB work shipped 408 KB). Playing cards now come from `@uzu-toolkit/reader/cards`; parts with files of their own get an entry of their own.
- **A game starts from a play button.** On the game-select list a tap only selects a game; the play button under the list starts it for everyone. A stray tap cannot put everyone into a game they cannot leave until it ends.
- **A guide line where players would guess, but not all the time.** A phase's screen may show a line or two on what to do now at its top, from the work's data. It sits inline in the content and scrolls out of view with it; no overlay or fixed display, and it does not hide by itself. No window to close (the 3 players would each spend a tap).
- **The introduction shows the cast and waits for everyone.** Whom you play, every part with its one-line description, and a ready button; the phase moves on once all are ready (`readyPhase`). No count of who is ready. Taking it back is a separate button, since every button says what it does and whether to tap it shows at a glance. No tabs, since the text is short.
- **The game list says how many play.** Each game shows its player count, who watches when the spectator sits out, and an optional one-line description from the work; the button under the list can carry the work's label for ending the phase.
- **Footer in two rows, the phase in the band is a button.** The footer's upper row holds the screen's actions with the one to press now at the right edge; the lower row holds options and state (the handouts to read back, the time left). The band's phase label becomes a pill with a down mark that opens the phase list; the footer no longer has a phase-list entry. Details in `docs/design.md`, Footer.
- **Sheets are modal.** While a sheet shows, the screen under it is inert (keyboard and screen reader), focus starts on its close button and returns to what opened it, and Escape closes it. The footer and the band stay usable.
- **Buttons name who and what they affect.** A button that moves everyone says so (`button.nextAll`, `handout.extend` says it adds 2 minutes for everyone); a mark-only advance button keeps an accessible name (`button.nextLine`); the last phase's empty screen says `button.end`.
- **Audit of the strict review (2026-11-13).** Adopted: sheet focus, Escape and inertness; wording of everyone-affecting buttons; the advance button's name; the last phase's button. Already fixed: buttons of the previous screen staying (#28; InterstellarBG only needed its submodule moved up). Not adopted: a blank required setting after the timer ends is by design (the phase ends on time, blank stays blank, the viewer shows it as unfilled; going back reopens editing). Left to other threads: handout tab and reading position kept per player, shrinking the band and footer on short screens, 320px width (the handout thread and the columns thread). Left as checks on the production host: connecting, reconnecting, a failed send, and the end screen after `ended`, which the host takes over.
- **The vote is a toolkit part.** Word wolf's vote moved from InterstellarBG, as an important part for other works (a culprit vote). The kit keeps a ballot in state (`ballot`, `castVote`, `ballotClosed`): one choice per voter, changeable until the last voter votes, no vote for yourself unless allowed. The reader's `Vote` shows the choices and how many have not voted. What a result means (a tie, a reversal) stays with the game.
- **Wide screens have columns, and the handouts stay beside the screen.** A screen 40em wide and 480px tall (in the screen's own em) takes 2 columns, 60em wide takes 3; phones keep one column in both orientations. Once the handout phase is over, the handouts stay in view on a wide screen, in the column(s) left of the current screen, instead of opening as a sheet from the footer; the current screen takes the last column. The footer's actions centre under the current screen. Screens before the handouts keep their single reading column. Details in `docs/design.md`, Layout.
- **The handout's tabs spread over columns where there is room, and the band gives way on small screens.** A handout takes a column per tab (about 18em each, up to 3) with the rest as tabs in the last, counted on its own width, so beside the screen it has fewer. The narrowest screen supported is 320px wide: under 380px the phase has a row above the players; names and long phase names end in an ellipsis. Under 480px tall the band's icons and names sit side by side and the band is shorter. Details in `docs/design.md`.
- **The handout post-game screen opens with the read-through's greeting.** `HandoutReviewView` shows `review.heading` above its parts row, the same greeting the read-through's post-game screen has, so a work with handouts and one without share one post-game screen.
- **Court cards drop Kennard's blue panel outline.** At card sizes of 3em to 4.5em the outline read as a stray frame around the figure. The figure's own art keeps its blue lines.
- **The reader's screens are replaceable defaults.** The screens stay in the toolkit as the default; a work replaces what it needs without a toolkit change: colours and sizes as tokens, any wording through `startFlow`'s `strings`, one phase's screen through its `view`, the whole frame (band, footer, sheets) through `shell`. The state, the sender, the footer's cells and the frame's parts are exported for this. (Screens kept in the toolkit with only the outer frame, wording and validation exits exposed, chosen over adding named props per request, headless-only parts, and copying the screens into each work.)
- **Phase wiring travels with the phase.** `handoutScreen` and `castScreen` return a phase's view, content and the wiring the shell reads (`reopen`, `keep`, `done`), so a new feature of a phase does not ask each work for more lines in `main.ts`.
- **Checks find screens by marks, not by class names.** The dev harness's tap-next and the screen preview's `next` and `scroll` look for `data-uzu-actions="main"`, `data-uzu-phase` and `data-uzu-scroll`, so they keep working when a work replaces the screens; the harness says so when it finds no main action.
- **The conditions for adding to the toolkit are not written down.** The owner chose not to record them as a rule; each addition is judged when it is asked for.
- **Works follow the toolkit by an automatic submodule update, not by hand.** A work that takes the toolkit as a submodule gets a scheduled workflow that moves the pin to the toolkit's main and opens one pull request; it rebuilds the work's font subsets when the glyph check fails. The toolkit keeps `CHANGELOG.md` in which every entry ends with `Work action:` (`none` or the step), and the update's pull request quotes the new entries so the work's owner sees at a glance whether anything is to be done. A change to a part's props, a string key, a data format, a command or the fonts needs an entry in the same toolkit pull request.
- **Font glyph lists come from the project's files, and a test guards them.** Each project (sample or work) lists in `fonts.config.json` which files and fields feed the story font and the UI font, so a work whose strings or data sit elsewhere only changes that file. A test fails when a subset lacks a glyph the project shows; one command rebuilds the subsets (`npm run fonts`).
